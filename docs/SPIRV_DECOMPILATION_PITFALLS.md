# Common SPIR-V-to-GLSL/Slang Decompilation Pitfalls

When working with shaders decompiled from SPIR-V bytecode back to GLSL (via SPIRV-Cross) or rewritten as Slang for RenoDX replacement, the decompiler often produces code that looks correct but has subtle semantic mismatches with the original bytecode. This document catalogs known issues to check for by cross-referencing the decompiled `.glsl` against the SPIR-V disassembly (`.frag_disasm.txt`).

## Toolchain Context

- **Source bytecode:** SPIR-V 1.3+ (generated by Google spiregg / DXC targeting Vulkan)
- **Decompiler:** SPIRV-Cross (produces `.glsl` with `#version 450`)
- **Replacement target:** Slang (`.frag.slang`) compiled via slangc → SPIR-V
- **Disassembly reference:** `spirv-dis` output (OpCodes with SSA IDs)

The SPIR-V disassembly is the ground truth. When the `.glsl` disagrees with the disassembly, the disassembly wins.

---

## 1. `OpPhi` flattening into broken `do { ... } while(false)` / single-iteration loops

**Severity:** Critical — loop body executes only once

SPIRV-Cross reconstructs control flow from SPIR-V's structured merge/continue semantics. When it fails to identify a loop back-edge, it may emit `do { ... continue; } while(false)` which executes exactly once regardless of the original iteration count.

**What to look for in the GLSL:**
```glsl
// WRONG — only one iteration
vec4 _274;
do {
    // ... body that should iterate ...
    _274 = some_value;
    continue;
} while(false);
```

**How to verify:** In the disassembly, look for `OpLoopMerge` and `OpBranchConditional` with a back-edge (branch target is the loop header). For example:
```
%238 = OpLabel
%244 = OpPhi %int %int_0 %235 %245 %241    ; induction variable
%246 = OpSLessThan %bool %244 %228          ; loop condition
       OpLoopMerge %247 %241 None           ; merge = %247, continue = %241
       OpBranchConditional %246 %241 %247   ; back-edge to %241
```

If the disassembly has `OpLoopMerge` + `OpPhi` with an incrementing induction variable, but the GLSL has `do { ... } while(false)`, the loop was incorrectly flattened. Reconstruct as a proper `for` loop.

**Correct reconstruction:**
```glsl
float _239 = 0.0;
vec4 _242 = vec4(0.0);
for (int _244 = 0; _244 < _228; _244++) {
    // ... loop body ...
}
```

## 2. `NMin` / `NMax` vs `min` / `max` — NaN propagation semantics

**Severity:** Medium to Critical — silent behavioral difference with NaN inputs

SPIR-V has two families of min/max:
- `OpExtInst GLSL.std.450 NMin/NMax` (id 79/80) — NaN-safe: if one operand is NaN, returns the non-NaN operand
- `OpExtInst GLSL.std.450 FMin/FMax` (id 37/38) — NaN behavior is undefined

SPIRV-Cross emits both as GLSL `min()`/`max()` by default. However, when targeting Vulkan with `GL_EXT_spirv_intrinsics`, it may emit `spvNMin`/`spvNMax` wrapper functions that use `spirv_instruction` to preserve the exact opcode.

**What to look for:**
```glsl
// These are NOT equivalent if NaN is possible:
float a = min(x, y);       // FMin — NaN behavior undefined
float a = spvNMin(x, y);   // NMin — guaranteed non-NaN result if one operand is valid
```

**How to verify:** Check the disassembly for the ExtInst ID:
```
%227 = OpExtInst %float %1 NMin %float_15 %226   ; id 79 = NMin
%263 = OpExtInst %float %1 NMax %float_9_99999975en06 %239  ; id 80 = NMax
```

If the disassembly uses `NMin`/`NMax` (ids 79/80), the GLSL must use `spvNMin`/`spvNMax` (or equivalent intrinsic declarations). If SPIRV-Cross emitted plain `min`/`max`, the NaN-safety guarantee is lost. In Slang replacements, use the appropriate intrinsic or guard against NaN explicitly.

**When this matters:** Any shader that divides (potential 0/0 = NaN) then clamps. The decay shader's `_242 / vec4(max(epsilon, _239))` pattern is safe because of the epsilon, but if the decompiler drops the NMin and uses plain min on the loop bound, a NaN loop count could cause infinite iteration or zero iterations.

## 3. UBO/SSBO struct layout mismatch — `std140` padding vs actual offsets

**Severity:** Critical — silently reads wrong uniform data, corrupting all downstream computation

SPIR-V encodes exact byte offsets for every struct member via `OpMemberDecorate ... Offset N`. SPIRV-Cross reconstructs a GLSL `layout(std140) uniform` block, but `std140` has implicit padding rules that may not match the original layout. If the decompiler's reconstructed struct doesn't match the SPIR-V offsets, fields read garbage.

**Common mismatches:**

| SPIR-V layout | std140 expectation | Problem |
|---|---|---|
| `float` at offset 224, `float` at offset 228 | Two floats packed in same vec4 | Correct — std140 allows this within a vec4 |
| `uint` at offset 236 after `float` at offset 232 | May insert padding to next vec4 boundary | Wrong if std140 pads but SPIR-V doesn't |
| `vec2` at offset 352 after `uint` at offset 348 | vec2 must be 8-byte aligned in std140 | Padding inserted, shifts all subsequent fields |
| `mat4` at offset 32 | Column-major, 16-byte stride per column | Must verify `MatrixStride 16` and `ColMajor` decorations match |

**What to look for in the GLSL:**
```glsl
layout(set = 4, binding = 0, std140) uniform type_cpost_processing_desc_cb
{
    ivec2 screen_size;      // offset 0 — OK
    ivec2 frame_size;       // offset 8 — OK
    // ...
    float time;             // offset 224
    float fade_amount;      // offset 228
    float overlay_intensity;// offset 232
    uint fade_enable;       // offset 236
    // ...
};
```

**How to verify:** Cross-reference every field against the `OpMemberDecorate` offsets in the disassembly:
```
OpMemberDecorate %type_cpost_processing_desc_cb 7 Offset 224   ; time
OpMemberDecorate %type_cpost_processing_desc_cb 8 Offset 228   ; fade_amount
OpMemberDecorate %type_cpost_processing_desc_cb 9 Offset 232   ; overlay_intensity
OpMemberDecorate %type_cpost_processing_desc_cb 10 Offset 236  ; fade_enable
```

If any field's actual byte offset under `std140` rules doesn't match the `OpMemberDecorate` offset, you need explicit `layout(offset = N)` qualifiers or restructure the block.

**For Slang replacements:** Use `packoffset(cN.x)` annotations (HLSL-style) which Slang respects when targeting SPIR-V. Verify the generated SPIR-V offsets match the original.

## 4. Matrix multiplication order — `OpMatrixTimesVector` vs `OpVectorTimesMatrix`

**Severity:** Critical — produces completely wrong transformed positions/directions

SPIR-V distinguishes:
- `OpMatrixTimesVector` — matrix × column vector (result is column vector)
- `OpVectorTimesMatrix` — row vector × matrix (result is row vector)

Combined with `ColMajor` vs `RowMajor` decorations on the matrix, the effective multiplication can be confusing. SPIRV-Cross generally handles this correctly, but when rewriting in Slang (which uses HLSL conventions: `row_major` by default, `mul(vector, matrix)` vs `mul(matrix, vector)`), getting the order wrong inverts the transform.

**What to look for:**
```glsl
// SPIRV-Cross output — matrix * vector (column-major convention)
vec4 _295 = cpost_processing_desc_cb.inv_viewproj_matrix * vec4(ndc_x, ndc_y, depth, 1.0);
```

**In the disassembly:**
```
%295 = OpMatrixTimesVector %v4float %286 %294
; %286 = inv_viewproj_matrix (decorated ColMajor, MatrixStride 16)
; %294 = the vector
```

**When converting to Slang:**
```hlsl
// If matrix is declared row_major in Slang (HLSL default):
float4 _295 = mul(float4(ndc_x, ndc_y, depth, 1.0), inv_viewproj_matrix);

// If matrix is declared column_major:
float4 _295 = mul(inv_viewproj_matrix, float4(ndc_x, ndc_y, depth, 1.0));
```

**How to verify:** Check the matrix decoration in the disassembly (`ColMajor` or `RowMajor`) and the operation (`OpMatrixTimesVector` or `OpVectorTimesMatrix`). Then ensure the Slang `mul()` argument order produces the same mathematical result. Getting this wrong flips the entire world-space reconstruction.

## 5. `OpSelect` with vector condition vs scalar condition

**Severity:** Medium — component-wise vs uniform select

SPIR-V `OpSelect` can operate with:
- A scalar `%bool` condition → selects entire vector A or B
- A vector `%v3bool` condition → selects per-component

SPIRV-Cross typically emits both as a ternary or `mix()`, but the semantics differ:
```glsl
// Scalar condition — selects whole vector
vec3 result = condition ? vec_a : vec_b;

// Vector condition — per-component (SPIRV-Cross may emit this as mix with bvec)
vec3 result = mix(vec_b, vec_a, bvec3(cond_x, cond_y, cond_z));
```

**How to verify:** Check the condition type in the disassembly. If `OpSelect %v3float %bool_scalar ...`, it's a uniform select. If `OpSelect %v3float %v3bool ...`, it's per-component.

## 6. Derivative operations (`dFdx`/`dFdy`) in non-uniform control flow

**Severity:** Critical — undefined behavior, may produce garbage or GPU hang

SPIR-V requires `OpDPdx`/`OpDPdy` to be in uniform control flow (all invocations in a quad must execute the same path). SPIRV-Cross faithfully emits `dFdx()`/`dFdy()` wherever the SPIR-V has them, but if you restructure the control flow during Slang rewrite (e.g., moving code inside a branch that wasn't there before), derivatives become undefined.

**What to look for in the original:**
```glsl
// These are OUTSIDE any non-uniform branch in the original:
vec3 _300 = dFdx(_299);
vec3 _301 = dFdy(_299);
```

**In the disassembly:**
```
%300 = OpDPdx %v3float %299
%301 = OpDPdy %v3float %299
```

**Rule:** When rewriting in Slang, ensure `ddx()`/`ddy()` calls remain at the same control-flow level as in the original. If you need derivatives inside a branch, compute them before the branch and pass them in.

## 7. `OpUndef` — uninitialized value placeholders

**Severity:** Low to Medium — usually harmless but can mask bugs

SPIR-V uses `OpUndef` to represent values that are never actually read (dead code, unused swizzle components). SPIRV-Cross emits these as uninitialized local variables:
```glsl
float _186;    // OpUndef %float
vec4 _187;     // OpUndef %v4float
vec4 _188;     // OpUndef %v4float
```

These appear at the top of the decompiled shader and are used as placeholders in composite constructions where only some components matter:
```glsl
vec4 _431 = vec4(_428.x, _428.y, _428.z, _187.w);  // .w is don't-care
_431.w = 1.0;  // immediately overwritten
```

**Risk:** If you accidentally use an `OpUndef` variable's value in a Slang rewrite (e.g., removing the subsequent overwrite), you get uninitialized memory reads. The GPU may return 0, NaN, or garbage depending on vendor.

**How to verify:** Search for `OpUndef` in the disassembly. Every corresponding variable in the GLSL should either be immediately overwritten before use, or only appear in dead swizzle positions. If you're cleaning up the shader, replace with explicit `0.0` for safety.

## 8. Sampler/texture combining — `OpSampledImage` lifetime rules

**Severity:** Compile error or driver crash — combined image+sampler used across basic blocks

SPIR-V requires that `OpSampledImage` results are consumed in the same basic block they're created in. SPIRV-Cross handles this correctly in its output, but when rewriting in Slang, you might be tempted to hoist a combined sampler outside a loop or branch:

```hlsl
// WRONG — combined sampler created outside loop, used inside
SampledImage combined = SampledImage(texture, sampler);
for (int i = 0; i < N; i++) {
    color += combined.SampleLevel(uv, 0.0);  // may violate block lifetime
}

// CORRECT — combine at point of use (compiler handles this)
for (int i = 0; i < N; i++) {
    color += texture.SampleLevel(sampler, uv, 0.0);
}
```

**How to verify:** In the disassembly, `OpSampledImage` always appears immediately before `OpImageSampleExplicitLod` or `OpImageSampleImplicitLod` in the same block. In Slang, just use the standard `texture.Sample(sampler, uv)` syntax and let the compiler handle combining.

## 9. Integer-to-float conversion — `OpConvertSToF` vs `OpConvertUToF` vs `OpBitcast`

**Severity:** Critical — wrong conversion produces garbage values for large integers

SPIR-V distinguishes:
- `OpConvertSToF` — signed int → float (preserves sign)
- `OpConvertUToF` — unsigned int → float (treats bits as unsigned)
- `OpBitcast` — reinterpret bits (like `intBitsToFloat` / `uintBitsToFloat`)

SPIRV-Cross usually gets this right, but in complex expressions the signedness can be lost:

```glsl
// If disassembly has OpConvertSToF:
float _197 = float(int_value);   // signed conversion — negative values become negative floats

// If disassembly has OpConvertUToF:
float _197 = float(uint_value);  // unsigned conversion — 0xFFFFFFFF becomes 4294967295.0

// If disassembly has OpBitcast:
float _197 = intBitsToFloat(int_value);  // bit reinterpretation — completely different result
```

**What to look for:** The `screen_size`, `frame_size`, and `dynamic_size` fields are `ivec2` (signed) in the UBO but are converted to float for UV math. Verify the disassembly uses `OpConvertSToF` (not `OpConvertUToF` or `OpBitcast`):
```
%197 = OpConvertSToF %v2float %196   ; signed int2 → float2
```

If SPIRV-Cross emits `vec2(ivec2_value)` this is correct (GLSL implicit conversion from int is signed). But if it emits `vec2(uvec2_value)` for what should be a signed conversion, negative values (which shouldn't occur for screen_size but might for other fields) would be wrong.

## 10. `OpCompositeConstruct` with swizzle reuse — redundant temporary vectors

**Severity:** Low (cosmetic) but can mask real issues during review

SPIRV-Cross often emits patterns like:
```glsl
vec4 _258 = vec4(_256, _257, 0.0, 0.0);
vec2 _259 = _258.xy;  // immediately extracts .xy from the vec4 it just built
```

This comes from SPIR-V's `OpCompositeConstruct` followed by `OpVectorShuffle`. It's semantically correct but obscures the actual data flow. When rewriting in Slang, simplify to:
```hlsl
float2 _259 = float2(_256, _257);
```

**Risk:** If you're tracing data flow to understand what a texture sample's UV is, these redundant constructions add noise. They're not bugs, but they make it harder to spot real issues.

## 11. `OpBranchConditional` with `DontFlatten` — forced branching semantics

**Severity:** Medium — performance difference, potential correctness issue with side effects

SPIR-V selection constructs can carry `SelectionControl DontFlatten` (equivalent to `[branch]` in HLSL). SPIRV-Cross emits these with the `SPIRV_CROSS_BRANCH` macro:
```glsl
SPIRV_CROSS_BRANCH
if (condition) { ... }
```

Which expands to `[[dont_flatten]]` when `GL_EXT_control_flow_attributes` is available.

**Why this matters for Slang rewrites:** If the original shader uses `DontFlatten` on a branch that contains texture samples with implicit derivatives, removing the branch hint (or restructuring into a flattened ternary) can cause the driver to flatten the branch, executing both sides. If one side has side effects or expensive texture fetches, this changes performance. More critically, if one side reads from a resource that isn't bound for certain draw calls, flattening causes an out-of-bounds read.

**How to verify:** Check the disassembly for `OpSelectionMerge %N DontFlatten`. Preserve `[branch]` in the Slang replacement for these.

## 12. Loop unroll hints — `OpLoopMerge` with `Unroll` vs `DontUnroll`

**Severity:** Low to Medium — performance, potential register pressure issues

SPIR-V loops can carry `LoopControl Unroll` or `LoopControl DontUnroll`. SPIRV-Cross emits these as:
```glsl
SPIRV_CROSS_UNROLL    // [[unroll]]
for (int i = 0; ...) { ... }

SPIRV_CROSS_LOOP      // [[dont_unroll]]
for (int i = 0; ...) { ... }
```

**Why this matters:** The decay shader's 30-iteration ray march loop likely has `DontUnroll` to prevent register explosion. If you rewrite in Slang without the `[loop]` attribute, the compiler may unroll it, massively increasing register pressure and potentially causing occupancy drops or shader compilation failures on some drivers.

**How to verify:** Check `OpLoopMerge` for loop control flags. Preserve `[unroll]` or `[loop]` attributes in Slang accordingly.

## 13. Descriptor set/binding mismatch between decompiled layout and actual pipeline

**Severity:** Critical — reads from wrong texture or crashes

SPIRV-Cross faithfully reproduces `layout(set = N, binding = M)` from the SPIR-V decorations. However, when writing a Slang replacement that will be injected via RenoDX's shader replacement system, the descriptor layout must exactly match the original pipeline's descriptor set layout.

**What to look for:**
```glsl
// Original GLSL (from SPIRV-Cross):
layout(set = 2, binding = 17) uniform texture2D source_sampler;
layout(set = 0, binding = 1) uniform sampler SamplerLinearClamp;

// Slang replacement must use matching Vulkan bindings:
[[vk::binding(17, 2)]]
Texture2D<float4> source_sampler : register(t17, space2);
[[vk::binding(1, 0)]]
SamplerState SamplerLinearClamp : register(s1, space0);
```

**How to verify:** Cross-reference `OpDecorate %var DescriptorSet N` and `OpDecorate %var Binding M` in the disassembly against your Slang `[[vk::binding(M, N)]]` annotations. Note the argument order difference: SPIR-V is `(set, binding)` in decorations but Slang/HLSL `[[vk::binding]]` is `(binding, set)`.

## 14. `OpCompositeExtract` / `OpVectorShuffle` index confusion

**Severity:** Medium — reads wrong vector component

SPIR-V uses zero-based indices for component extraction:
- `OpCompositeExtract %float %vec4_var 0` → `.x`
- `OpCompositeExtract %float %vec4_var 2` → `.z`
- `OpVectorShuffle %v2float %v4a %v4b 2 3` → `vec2(a.z, a.w)`
- `OpVectorShuffle %v2float %v4a %v4b 4 5` → `vec2(b.x, b.y)` (indices ≥ 4 index into second operand)

SPIRV-Cross handles this correctly in almost all cases, but when `OpVectorShuffle` uses indices from both source vectors, verify the GLSL swizzle matches:

```
%222 = OpVectorShuffle %v2float %221 %221 2 3   ; .zw of same vector
```
Should produce:
```glsl
vec2 _222 = _221.zw;  // correct
```

**When this goes wrong:** If SPIRV-Cross encounters an `OpVectorShuffle` with an `0xFFFFFFFF` index (undefined component), it may emit an arbitrary component. Check for any swizzle that seems wrong by tracing back to the `OpVectorShuffle` indices.

## 15. Floating-point constant precision — SPIR-V `OpConstant` vs GLSL literal

**Severity:** Low to Medium — accumulated precision drift in long computation chains

SPIR-V stores float constants as exact IEEE 754 bit patterns. SPIRV-Cross emits them as decimal literals with enough digits to round-trip, but occasionally truncates:

```
%float_0_0142857144 = OpConstant %float 0.0142857144   ; exact: 1/70
```
Emitted as:
```glsl
float val = 0.014285714365541934967041015625;  // full precision preserved
```

**When this matters:** For constants that are rational fractions (1/70, 1/30, etc.), using the exact decimal from SPIRV-Cross is fine. But if you're rewriting in Slang and simplify to `1.0 / 70.0`, the compiler may produce a slightly different constant due to compile-time vs runtime division. For most shaders this is negligible, but in iterative computations (ray marching, decay propagation) tiny differences can accumulate.

**Best practice:** Copy the exact decimal literal from the SPIRV-Cross output into your Slang replacement rather than computing it from a fraction.

## 16. `OpImageSampleImplicitLod` vs `OpImageSampleExplicitLod` — LOD selection

**Severity:** Medium — wrong mip level, blurry or aliased textures

SPIR-V distinguishes:
- `OpImageSampleImplicitLod` — uses implicit derivatives (only valid in fragment shaders, uniform control flow)
- `OpImageSampleExplicitLod ... Lod %float_0` — explicit LOD 0 (mip 0, sharpest)

SPIRV-Cross emits:
```glsl
texture(sampler2D(tex, samp), uv);           // ImplicitLod
textureLod(sampler2D(tex, samp), uv, 0.0);   // ExplicitLod with Lod 0
```

**Why this matters for Slang rewrites:**
- `texture.Sample(sampler, uv)` → implicit LOD (uses derivatives)
- `texture.SampleLevel(sampler, uv, 0.0)` → explicit LOD 0

If the original uses `ExplicitLod` with LOD 0 (common inside loops or non-uniform branches where implicit derivatives are invalid), your Slang replacement must use `SampleLevel`, not `Sample`. Using `Sample` inside a loop produces undefined derivatives and the driver picks an arbitrary mip level (usually the lowest resolution).

**How to verify:** For every texture fetch inside a loop or branch, check the disassembly. If it's `OpImageSampleExplicitLod`, use `SampleLevel` in Slang.

## 17. Push constant / injection data struct alignment

**Severity:** Critical — all injected settings read as garbage

When adding RenoDX push constants (`[[vk::push_constant]]`) to a replacement shader, the struct layout must match exactly what the C++ side pushes. Vulkan push constants follow `std430`-like packing (no implicit padding between scalars), but Slang may insert padding if you use types that trigger alignment requirements.

**What to look for:**
```hlsl
// shared.h defines the struct for both C++ and shader:
struct ShaderInjectData {
    float peak_white_nits;      // offset 0
    float diffuse_white_nits;   // offset 4
    float graphics_white_nits;  // offset 8
    // ...
};
```

**Rule:** Every field in the push constant struct must be a 4-byte scalar (`float`, `uint`, `int`). Do not use `float2`, `float3`, `float4`, or `bool` (which may be 1 byte in C++ but 4 bytes in HLSL). The `shared.h` pattern used in this project (dual C++/HLSL header) handles this correctly — don't deviate from it.

**How to verify:** Count bytes in the C++ struct and verify they match the shader struct. If using the devkit, inspect push constant data at runtime to confirm values arrive correctly.

## Verification Checklist

When reviewing a SPIRV-Cross decompiled shader before writing a Slang replacement:

1. **Loops:** Search for `do { ... } while(false)` and `while(true) { ... break; }` — cross-reference against `OpLoopMerge` + `OpPhi` in the disassembly to verify iteration count
2. **NMin/NMax:** Verify `spvNMin`/`spvNMax` usage matches ExtInst ids 79/80 in disassembly — don't downgrade to plain `min`/`max`
3. **UBO layout:** Cross-reference every struct field offset against `OpMemberDecorate ... Offset N` — watch for std140 padding mismatches
4. **Matrix multiply order:** Verify `OpMatrixTimesVector` vs `OpVectorTimesMatrix` and `ColMajor`/`RowMajor` decorations match your Slang `mul()` argument order
5. **Integer conversions:** Check `OpConvertSToF` vs `OpConvertUToF` vs `OpBitcast` — ensure GLSL/Slang uses the matching conversion
6. **Texture sampling:** Verify `ImplicitLod` vs `ExplicitLod` — use `Sample` vs `SampleLevel` accordingly, especially inside loops
7. **Descriptor bindings:** Confirm `[[vk::binding(binding, set)]]` matches `OpDecorate ... DescriptorSet/Binding` (note argument order swap)
8. **Branch hints:** Preserve `[branch]`/`[flatten]` from `DontFlatten`/`Flatten` selection controls
9. **Loop hints:** Preserve `[loop]`/`[unroll]` from `OpLoopMerge` loop control flags
10. **OpUndef variables:** Identify uninitialized placeholders — ensure they're never read without being overwritten first
11. **Derivatives:** Ensure `dFdx`/`dFdy`/`ddx`/`ddy` remain in uniform control flow — don't move them inside non-uniform branches
12. **Push constants:** Verify struct layout matches `shared.h` exactly — no padding, no reordering, all 4-byte scalars
13. **Swizzle patterns:** For any suspicious component access, trace back to `OpVectorShuffle`/`OpCompositeExtract` indices in the disassembly
14. **Float constants:** Copy exact decimal literals from SPIRV-Cross output rather than recomputing from fractions

## Cross-Referencing Workflow

For each shader being analyzed or rewritten:

1. **Obtain both files:**
   - `0xHASH.frag.glsl` — SPIRV-Cross decompiled GLSL
   - `0xHASH.frag_disasm.txt` — `spirv-dis` disassembly

2. **Identify the entry point:** Look for `OpEntryPoint Fragment %mainPS "mainPS"` and the corresponding `%mainPS = OpFunction`

3. **Map SSA IDs to GLSL variables:** SPIRV-Cross names variables `_NNN` where NNN is the SPIR-V SSA ID. So `_295` in the GLSL corresponds to `%295` in the disassembly. This is your primary cross-reference tool.

4. **Verify control flow:** Compare `OpSelectionMerge`/`OpLoopMerge` structure against the GLSL `if`/`for`/`while` structure. Every `OpLoopMerge` should correspond to a real loop.

5. **Verify data flow:** For any suspicious computation, trace the SSA chain in the disassembly backward from the output to the inputs, verifying each operation matches the GLSL.

6. **Write the Slang replacement:** Use the verified GLSL as your starting point, converting syntax but preserving semantics. Add RenoDX modifications (push constants, tonemap calls, etc.) on top of the verified base.

## GLSL-to-Slang Conversion Reference

When converting a verified `.glsl` decompilation to a `.slang` replacement shader, apply the following transformations. Most of the time renaming `.glsl` to `.slang` works directly — when it doesn't, it's a compile error (not a logic error), and the fixes are purely syntactic.

Reference: [Migrating to Slang from GLSL](https://shader-slang.org/docs/coming-from-glsl/)

### Type Renames

| GLSL | Slang |
|------|-------|
| `vec2` / `vec3` / `vec4` | `float2` / `float3` / `float4` |
| `ivec2` / `ivec3` / `ivec4` | `int2` / `int3` / `int4` |
| `uvec2` / `uvec3` / `uvec4` | `uint2` / `uint3` / `uint4` |
| `bvec2` / `bvec3` / `bvec4` | `bool2` / `bool3` / `bool4` |
| `mat3` / `mat4` | `float3x3` / `float4x4` |
| `mat3x4` / `mat4x3` | `float3x4` / `float4x3` |

### Function Renames

| GLSL | Slang |
|------|-------|
| `mix(a, b, t)` | `lerp(a, b, t)` |
| `fract(x)` | `frac(x)` |
| `inversesqrt(x)` | `rsqrt(x)` |
| `atan(y, x)` | `atan2(y, x)` |
| `dFdx(x)` / `dFdy(x)` | `ddx(x)` / `ddy(x)` |
| `mod(x, y)` | `fmod(x, y)` (note: different sign behavior — see below) |

### Matrix Multiplication

**Critical difference:** GLSL uses `*` operator with column-major convention. Slang uses `mul()` with the arguments in a specific order.

```glsl
// GLSL: matrix * column_vector (ColMajor)
vec4 result = matrix * vector;
// GLSL: row_vector * matrix
vec4 result = vector * matrix;
```

```hlsl
// Slang: matrix * column_vector
float4 result = mul(matrix, vector);
// Slang: row_vector * matrix (or equivalently, transpose convention)
float4 result = mul(vector, matrix);
```

**Project convention:** This project declares matrices as `row_major` in the cbuffer and uses `mul(vector, matrix)` for the equivalent of GLSL's `matrix * vector` with ColMajor. See the existing uberpost shader for the established pattern.

### NMin/NMax Intrinsics

The `spvNMin`/`spvNMax` declarations using `spirv_instruction` don't exist in Slang. Replace with standard `min`/`max` — Slang's `min`/`max` on Vulkan targets compile to `OpExtInst NMin`/`NMax` by default (NaN-safe). If you need explicit control, use `__spirv_asm` or trust that the Slang compiler emits NaN-safe variants for float min/max.

```glsl
// GLSL (SPIRV-Cross output)
spirv_instruction(set = "GLSL.std.450", id = 79) float spvNMin(float, float);
float result = spvNMin(a, b);
```

```hlsl
// Slang — just use min/max
float result = min(a, b);
```

### Common Gotchas When Renaming .glsl → .slang

1. **`#version 450` and `#extension` lines** — Remove them. Slang doesn't use these.
2. **`layout(...)` on uniforms** — Convert to `[[vk::binding(binding, set)]]` + register syntax.
3. **`in`/`out` qualifiers** — Convert to struct-based I/O with semantics.
4. **`gl_FragCoord`** — Becomes a `SV_Position` input in the entry point struct.
5. **Implicit int→float conversion** — GLSL allows `vec2(ivec2_val)` implicitly. Slang requires explicit `float2(int2_val)` or `asfloat()`.
6. **`const` arrays at file scope** — Slang may require `static const`.
7. **`sampler2D(texture, sampler)` combined sampling** — Must be split into `texture.SampleLevel(sampler, uv, lod)` method calls.
8. **Matrix `*` operator** — Must become `mul()`. For GLSL `mat * vec` (OpMatrixTimesVector), use `mul(mat, vec)` in Slang. Despite the Slang docs suggesting the argument order is inverted, when targeting SPIR-V with `[[vk::binding]]` the compiler emits the correct `OpMatrixTimesVector` from `mul(mat, vec)`. This applies to both cbuffer matrices and locally-constructed matrices (TBN, etc.). Verified empirically — do NOT use `mul(vec, mat)` for `OpMatrixTimesVector`.
9. **`unpackHalf2x16` / `packHalf2x16`** — Use `f16tof32()` / `f32tof16()`. Note: `unpackHalf2x16(x).x` → `f16tof32(x)` (returns single float from low 16 bits). For the high half: `unpackHalf2x16((x >> 16u) & 0xFFFF).x` → `f16tof32((x >> 16u) & 0xFFFF)`.
10. **`floatBitsToUint` / `uintBitsToFloat`** — Use `asuint()` / `asfloat()`.
11. **`lerp` with `bvec` / `bool4`** — GLSL `mix(a, b, bvec4(cond))` uses a boolean vector to select per-component. Slang's `lerp` doesn't accept `bool4` as the interpolant. Replace with a ternary: `(cond) ? b : a` for scalar conditions, or use `select(a, b, bool4(...))` for per-component selection.
12. **Input location gaps require `[[vk::location(N)]]`** — If the GLSL shader has non-contiguous `layout(location = N)` on its inputs (e.g., locations 0–6 then 8–13, skipping 7), Slang will assign locations sequentially based on TEXCOORD index unless you explicitly annotate with `[[vk::location(N)]]`. Without this, every varying after the gap reads from the wrong vertex shader output, producing garbage (flat colors, wrong normals, broken UVs). Always cross-reference the GLSL `layout(location = N)` values and add explicit `[[vk::location(N)]]` to the Slang input struct members when there are gaps or when locations don't match the TEXCOORD index.
